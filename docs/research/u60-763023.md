# U60 763023: door owners, support buildings and leaked subscriptions

Build 763023 replaced 762230 on Steam's `public_testing` branch on 2026-11-12. Unlike 762230 it is
a content update as well as fixes: Klei's notes list 10 changes and 23 fixes, and the build
changes `Assembly-CSharp.dll` (63 files in the decompile), firstpass (two files), the FMOD
banks, the DLC bundles, the strings and the serialized data. Every Unity module and package, the
BCL, the other libraries, the FMOD libraries and the Linux `libSimDLL.so` are 762230's bytes, and
the Unity version is still 6000.3.17f1. The `u60` branch now targets 763023; this page is the
delta, its impact on Moono, and the QA results. `u60-762230.md` covers the build before it.
U59 (the default branch) did not change: its main depot's manifest is still 744825's
(4837644823067158760, 2026-07-28), so `master` is untouched.

Sources:
- Klei's decompiled game code in oni-versioning: `git diff U60-762230 U60-763023` (`49849cb1`
  to `5ddebdeb`), beta against beta, so the diff is code. `u763023:File.cs:N` is a line of
  `OxygenNotIncluded/File.cs` at tag U60-763023. The decompile was made as 762230's was:

- The frozen builds `E:\oni-builds\oni-linux-762230`, `oni-linux-763023`, `oni-win-762230` and

## Summary

- **Moono plays 763023** after one fix: `path-probe-repair`'s patch of
  `Grid.RegisterRestriction` by name became ambiguous (Klei added an owner overload), so the
  tweak would not install on 763023 and `check.sh` on `u60` went red once the build was frozen.
  It now patches each overload by signature (see "path-probe-repair"). Every other tweak
  installs unchanged: no fingerprinted body differs from 762230's.
- **Version check:** the Unity version is unchanged (6000.3.17f1), so the version check lets the
  current `u60` release start on 763023 too. Without the fix, that release runs with
  `path-probe-repair` off (its install fails, the tweak stands down, the game runs as without
  it).
- **Public API:** three members mods can bind to are gone (`STRINGS.DUPLICANTS.ATTRIBUTES.
  YIELDAMOUNT`, firstpass `KAnim.Anim.Frame.hasHead`, `ClusterManager.CanSave`'s setter), and
  some are added (see "Mods"). None of them is Moono's.
- **Klei's Linux renderer default** ("OpenGL is once again the default for Linux") is not in the
  build's data: `PlayerSettings` in `globalgamemanagers` is the same bytes in both builds. It is
  most likely Steam's launch configuration (not verified). Moono's renderer choice is its own
  (`auto`: Vulkan, OpenGL as the fallback), so this changes nothing for Moono.
- **QA:** check.sh and check-tweaks pass on every U60 build; the Linux quick QA (smoke, V1,
  the Vulkan gate, `path-probe-repair` with verify on) and a Windows Vulkan smoke on a late-game
  save pass. The Windows harness was slow on late-game saves in both players because of E2eDriver
  itself, fixed (see "QA results").

## The code delta

`git diff --stat U60-762230 U60-763023`: 63 files, 48,150 lines added and 47,701 removed, nearly
all of them the generated script table (`UnitySourceGeneratedAssemblyMonoScriptTypes_v1`, about
95,000 lines). That table is not reordered: its 3,807 files are the same and in the same order,
and its 15,565 types become 15,571 with the common ones in the same order. The added types are
`Blueprints_CosmeticPack2_U60`, `STRINGS.DUPLICANTS.ATTRIBUTES.YIELDFACTOR`,
`CREATURES.STATUSITEMS.HIDINGFROMMETEORS` and four `SANDSCULPTURE_*` string classes; the one
removed is `YIELDAMOUNT`. The insertions shift the table's 10-bytes-a-line wrapping, which is
why its diff is so large.

Firstpass: `KAnim.cs` renames `Anim.Frame.hasHead` to `preventSpeech` (fp763023:KAnim.cs:32), and
`KGlobalAnimParser.cs` also sets it for a frame with a `snapto_mouth` element whose frame is not 0
(fp763023:KGlobalAnimParser.cs:15,151-153). Its one reader is `SpeechMonitor`
(u763023:SpeechMonitor.cs:218).

### Changes the notes do not mention

- **Doors have owners.** `Grid.Restriction.ownerInstanceID`, `RegisterRestriction(cell,
  orientation, owner)` and `UnregisterRestriction(cell, owner)`, which removes a restriction
  only when the cell has none or it is that door's (u763023:Grid.cs:843-873). `AccessControl`
  passes its instance ID (u763023:AccessControl.cs:298-344), so a door being removed no longer
  clears another door's permissions on a shared cell. Path finding reads the permissions; see
  "path-probe-repair".
- **Leaked event subscriptions.** `KMonoBehaviour.Unsubscribe(int)` takes a subscription's
  handle (fp763023:KMonoBehaviour.cs:234); these classes passed an event hash, which removed
  nothing. They now keep the handle and use `Unsubscribe(ref handle)`: `FetchAreaChore` (the
  fetch crash), `FetchDrone` (which also unsubscribed from itself, not from its storage),
  `BaggableCritterCapacityTracker`, `IdleCellSensor`, `MegaBrainTank`,
  `ResuscitateSuffocatedChore`, `TemperatureOverlayInfraredVisualizerBase`, `TravelTube` and
  `ArtableSelectionSideScreen`.
- **Save blockers.** `ClusterManager.CanSave` was an auto-property with a private setter; it is
  now `isSpawned && saveBlockerCount == 0` (u763023:ClusterManager.cs:79), with
  `AddSaveBlocker`/`RemoveSaveBlocker` (counted, not saved) and
  `PendingRocketInteriorDestruction.saveBlockerID`. `Game.CanSave` reads it. Moono's save
  tweaks don't read `CanSave` (`background-save` saves when the game does).
- **Fertility** is bounded at 0 like the growth amounts (u763023:Database/Amounts.cs:128).
- **Hatch cosmetic permits** moved from `Blueprints_CosmeticPack2` into a new
  `Blueprints_CosmeticPack2_U60`; neither is listed in `Blueprints.skinsReleaseProviders`
  (u763023:Blueprints.cs:7), so both stay dormant.
- **Strings:** Turbo Mode tooltips get links, "(Turbo)" → "(Turbo Mode)", roller-coaster
  tooltips reworded, `MISC.ORGANICS` a link.
- **The build number** 762230 → 763023: `KleiVersion.ChangeList`, `SaveGame.GetSaveHeader`,
  `Game` (twice), `Global`, `KCrashReporter`, `KMod.Mod.GetMostSuitableArchive`, `LoadScreen`
  (three places), `MainMenu`, `BuildWatermark`, `PerformanceCaptureMonitor`. The save minor
  version stays 39, and no `[Serialize]` field was added.

## The fetch crash

762230's `FetchAreaChore.StatesInstance.SetFetchTarget` subscribed to the item's MarkForMove
event with a handle (u762230:FetchAreaChore.cs:451), but two of its three ways out,
`OnMarkForMove` itself and the `fetching.pickup` exit, unsubscribed with
`Unsubscribe_obsolete(hash, OnMarkForMove)`, which compares a new delegate with the stored one
and never matches. After a pickup the item kept a subscription to a finished chore's
StatesInstance, and a later MarkForMove (a Movable's, u763023:Movable.cs:240) ran it. 763023
sends both through `UnsubscribeMarkForMove`, `target.Unsubscribe(ref handle)`
(u763023:FetchAreaChore.cs:616,629,718), as `FetchFail` already did. Neither `Pickupable` nor
`FetchManager` changed, and neither does any method our fetch tweaks (`fetch-by-cell`,
`fast-offset-tables`) patch or mirror.

## path-probe-repair

The tweak keeps a change feed of everything a path probe's link evaluation reads, through the
game's writers; door permissions are `Grid.restrictions` and `Grid.HasAccessDoor`, written by
`RegisterRestriction`, `UnregisterRestriction`, `SetRestriction` and `ClearRestriction`, each
patched with a postfix that marks its cell. 762230 had one overload of each.

763023's writers (every caller is `AccessControl`):
- `RegisterRestriction(cell, orientation, owner)` writes both tables (u763023:Grid.cs:850-858);
  `RegisterRestriction(cell, orientation)` passes owner 0 to it, and nothing in the game calls it
  any more.
- `UnregisterRestriction(int)` writes both (u763023:Grid.cs:861-865);
  `UnregisterRestriction(cell, owner)` calls it when the cell has no restriction or the owner
  matches, and otherwise writes nothing.
- `SetRestriction` and `ClearRestriction` are unchanged; `ResetNavMasksAndDetails` clears the
  table when the grid is set up, before any probe.

`AccessTools.Method(typeof(Grid), name)` with two overloads throws `AmbiguousMatchException`, so
the tweak's install failed: on 763023 it was off (logged, the game ran as without it), and
`check-tweaks` failed. The tweak now patches by signature: both registrations where the build
has both (the owner's declared `Optional`), the one-cell removal, and the other two as before.
Every write still marks its cell, on 763023 and on the older U60 builds; on 763023 a
registration marks its cell twice (the forwarding overload's postfix runs too), which only adds
an event. The verify mode's audit (`FeedAudit`) hashes each restriction's fields, so the new
`ownerInstanceID` is part of what it compares.

`GameMember`'s `Optional` passed only when no member of the name was in the game, so an overload
that a build adds beside an older one failed as "changed" on the builds without it. An optional
method now passes whenever its exact signature is absent. The other overloads still need their
own declarations, which fail when they change; fields are checked as before
(`TweakChecks.Declared`).

**instant-reachability** patches and guards `MinionGroupProber`, `Workable`, `OffsetTracker`,
`OffsetTableTracker`, `Pickupable.UpdateCachedCell`, `ReachabilityMonitor` and `Game.Update`;
none of them changed. Door permissions are an input of path costs and reachable cells, which the
game's own probes compute and the tweak takes from them as before. The owner check changes which
permissions survive a door's removal (another door's restriction on a shared cell stays): game
behaviour that both players follow, through the writers above.

## Other game tweaks and IL rewriters

`check-tweaks --review` on `linux-763023`, `win-763023` and `linux-762230`: every tweak passes
the file checks (declared members, references, reviewed fingerprints, name lookups) on 763023,
and the only install that failed was `path-probe-repair`'s. The 95 normalised listings of
fingerprinted bodies are the same bytes for 762230 and 763023, and for Linux and Windows. Each
accepted fingerprint now lists `linux-763023` and `win-763023`, including `sim-step-pace`'s
`Game.SimEveryTick`, which landed on `u60` after the review (its source is unchanged). The types
our tweaks declare members of that Klei changed are `Game`, `Grid`, `LoadScreen` and `MainMenu`.
In `Game`, `LoadScreen` and `MainMenu` only build constants changed, in bodies no tweak
fingerprints; in `Grid`, only the restriction methods above changed.

`fmod-steal-fix` patches FMOD Studio's library only when its SHA-256 matches: 763023's
`fmodstudioL.dll` and `libfmodstudioL.so` are 762230's files, so its U60 rows now name 761015
to 763023.

The IL rewriters (`MonoConversions`, the abort rewrite, `NavGridLinksRewrite`,
`PathGridPagesRewrite`) match methods by name and signature; their counts on 763023 are in "QA
results".

## The host, the engine and our API

- **Version check.** `GameVersionCheck` compares the data's Unity version (6000.3.17f1 → U60);
  unchanged.
- **Natives.** `check-natives` (in `check.sh`) passes on 763023: every entry point the install's
  plugins need is exported. SimDLL's Windows DLL differs from 762230's in 30 bytes, as in the
  updates before: the PE and debug timestamps, the build constant and the PDB GUID. The Linux
  `libSimDLL.so` is the same bytes.
- **The Workshop item.** Its U60 version now asks for build 763023 (`minimumSupportedBuild`,
  `scripts/workshop-item.py`); the loader mod builds against 763023's reference assemblies.
- **Engine.** None of the changed code calls an engine member that 762230 did not already call
  (the new code uses `KFMOD.PlayOneShot`, `KAnimLink`, coroutines and `Object` equality). The
  `ReorderableBuilding` coroutine relies on a destroyed `WorldContainer` being gone within ten
  frames, which is when the engine carries out destruction, as Unity does (not run).
- **Performance.** `AttributeInstance.GetTotalValue` and `GetTotalDisplayValue` now clamp on
  every read, with two `DevOnly.Assert` calls compiled in (the assembly is built with
  `DEVELOPMENT_BUILD`). That is extra cost on a frequent read, the same in both players, so
  perf figures taken on 762230 are not directly comparable with 763023's (not measured).

### The Windows harness's slow frames

The first Windows smoke on the late base ran at about 4 fps in ours and below 1 in the original.
It was the harness, not the build: frame stats' `script time` gave E2eDriver's
`SyntheticInput.Update` 191 ms a frame (`Game.Update` 17 ms), as it attached its input override
with `FindObjectsOfType<BaseInputModule>()` every frame, a walk over every live object; the
original on 762230 was as slow as on 763023 (both 10-minute runs ended after about 40 game
seconds). E2eDriver now attaches once a second (and before each input request): ours' update
went from about 220 ms to 11-12 ms a frame, 60 game seconds in 46 s instead of 89, and the
original's 60 game seconds took 86 s. Neither player was throttled: Normal priority, EcoQoS off,
the CPU at its rated clock, one thread busy all the time. Linux runs never start synthetic input.

### The mod gate

`scripts/mod-gate.py` reads onimaxxing's `mods-data/BUILD`, BUILD from the game folder's name
unless `ONI_GAME_BUILD` names one. On `u60` that is 763023, and onimaxxing has no data for it:
`catalog.json` answers 404 for 763023, as for 761654, 762107 and 762230. 744825 (U59) and 761211
answer 200, both generated on 2026-11-12 (761211's names 744825 as its previous build), 3,111
mods each. With no data, every mod with binaries is skipped ("not reviewed by onimaxxing yet:
upload N is not analysed"), so the gate fails closed: mod runs on `u60` still need
`ONI_GAME_BUILD`.

A sample of 60 unpacked mods (`out/ws` of the main checkout): 8 pass and 52 are skipped with
763023 (the 8 have no binaries); with `ONI_GAME_BUILD=744825` and with 761211 all 60 pass, for
the same reasons, line for line. The cross-build reviews work as intended: a review is of an
upload, whatever the build.

Fast Track's GitHub build (`9000000001`) is skipped on `u60` ("SteamCMD records no upload handle
for it"): the gate's GitHub-build hashes (master's 8d2e8a42) are not on `u60`. It would not load
there anyway (below).
