# U60 762107: sandbox, Aquatic and drag-to-build fixes

Build 762107 replaced 761654 on Steam's `public_testing` branch on 2026-11-05. It is a fix
update: game code and data only. Only `Assembly-CSharp.dll` changed among the managed
assemblies; firstpass, every Unity module and package, the BCL and the other libraries are
761654's bytes, and the Unity version is still 6000.3.17f1. The `u60` branch now targets 762107;
this page is the delta, its impact on Moono, the QA plan and its results. `u60-761654.md` covers
the build before it.

## Summary

- **Moono plays 762107.** `u60` (f4485e4b) loads early-base and plays 180 game seconds at speed 3
  on Linux, as the original does on the same install; the IL rewriters' counts and every game
  tweak's install line are 761654's (see "Smoke test").
- **Nothing in Moono needed a fix for 762107.** No engine member the game references was added
  or removed (`tools/Inventory`: the same 6,822 entries), no Unity or library assembly changed,
  and no game tweak patches a method that changed beyond `fix-endless-sounds`'s data rows.
- **`fix-endless-sounds` is removed on `u60`.** 762107's audio sheets build the adult Pip's
  `eat_loop` row and the rocket debris' `landed` row as `LoopingSoundEvent`, the two rows the
  tweak rebuilt, and two more rows too. On 762107 the tweak saw the rows' new type, changed
  nothing and logged `fix-endless-sounds: left out for … its type is LoopingSoundEvent` for each
  (X2, measured before the removal); since the game fixes it, the tweak is gone from `u60` (see
  "Game tweaks"). `master` keeps it: U59 744825 still has the bug.
- **The drag-to-build fix** (`BaseUtilityBuildTool.OnDragTool` fills a diagonal step) runs on
  the pointer positions the game samples each frame; X1 drags a wire diagonally in both players
  and gets the same five joined wires.
- **QA:** X1-X7 pass in both players on Linux, and each detects its change in the 761654 original;
  68 of the 77 U60 specs pass in both, the others fail in the original by themselves, need a
  setup the test install lacks, or are known (one pre-existing difference, one repro by design).
  Windows: both players load and play at speed 3, the side buttons match, the Restarter brings
  ours back. check.sh is green on 762107 (see "QA results").

### Changes the notes do not mention

  delegate instead of an `IComparer<T>` class, same order rules (u762107:GlobalChoreProvider.cs:98-107,
  235; ClearableManager.cs:23-27). In Mono's `mscorlib` (the game's `Managed/`) `List<T>.Sort

## The drag-to-build fix

A utility tool drags in brush mode: each frame `DragTool.OnMouseMove` samples the pointer's way
from the previous frame's position at quarter-cell steps and calls `OnDragTool` for each sampled
cell that is valid and visible (u762107:DragTool.cs:431-454). A drag along a 45° line through
cell centres crosses each cell corner exactly, so consecutive samples step diagonally:
761654 then added the diagonal cell to the path, and `BuildPath` laid unconnected pieces. 762107
first adds the cell in the last cell's row, `(x2, y)`, by calling itself (u762107:
BaseUtilityBuildTool.cs:110-122).

What Moono supplies is the pointer: `Input.mousePosition` from the platform's events, once a
frame. The samples lie on the pointer's way whatever the frame rate; the frame rate only decides
how many fall in one frame. Neither the tweaks (none patches `DragTool`, `BaseUtilityBuildTool`,
`BuildTool` or `Grid`) nor the path and nav-grid rewrites (`NavGridLinksRewrite`,
`PathGridPagesRewrite`, `compact-nav-links`, `paged-path-grids`, `path-probe-repair`) touch this
path: building a utility changes the nav grid only once the building exists. X1 measures it.

### X1 drag-to-build

The first form of the spec dragged in 12 pointer steps (7.5 px at 45 px a cell). Rounded to
whole pixels, those positions leave the diagonal by a pixel, and each crossing of a cell corner
splits into a row crossing and a column crossing in different frames: a staircase, joined in
761654 too (5 wires in the `ctl761654` control). With 9 steps of 10 px every position lies on the
diagonal, the brush's quarter-cell samples cross row and column in the same step, and 761654
lays 3 unconnected wires where 762107 lays 5 (run ids `x1e`, `x1ctl`). Ours on OpenGL samples
the same way: 5 wires, the same positions.

Before picking the Wire, the spec plays 30 game seconds: right after the load the original's
colony inventory counts 0 kg of Copper Ore for a while at llvmpipe's frame rate (what the
Duplicants can reach comes from path probes spread over frames), so its build menu offered the
Wire's requirements (PrebuildTool) and the drag laid nothing; ours, at many more frames a second,
had 1,595 kg by then. A frame-rate effect in the game's own reachability, not a difference in
outcome.

### X3 sandbox placement

The pop-ups are counted on `PopFXManager.SpawnFX`'s last overload (every other ends in it), the
sounds on `SoundEvent.BeginOneShot(string, …)`. Both are read right after the placement, with the
game paused: one-second runs between them let Duplicants pop their own pop-ups (2 in the
original, 1 in ours in one run). The Ladder is counted as `BuildingComplete`: an instant build
leaves its under-construction object for a frame, which `Building` also counts. In the original
on llvmpipe a click's move and press can land in one frame, and the brush then lays Ladders along
the pointer's way from the material panel; the spec hovers the cell first.
